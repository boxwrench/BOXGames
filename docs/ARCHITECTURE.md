# Architecture

## The split

BOXGames holds several game demos. The organising question for any file is:
**would a second demo want this?**

| Answer | Home |
| --- | --- |
| Yes, it's code | `shared/` |
| Yes, it's knowledge | `docs/` |
| Yes, it's offline tooling | `tools/` |
| No — only this demo | `games/<game>/` |

Shared code must earn its place. Something used by exactly one demo lives in
that demo until a second one needs it; premature sharing produces packages
shaped around a single caller.

## Layout

```
BOXGames/
├── go.work                  workspace tying the modules together
├── Makefile                 thin delegation to scripts/
├── scripts/                 bootstrap and build
├── docs/                    cross-cutting docs (this file, SETUP, KAIJU-NOTES…)
├── shared/                  module: boxwrench.dev/boxgames/shared
│   ├── kaijuboot/           layered content database, game bootstrap
│   ├── palette/             boxwrench design tokens as engine colors
│   ├── pool/                fixed-capacity object pools
│   ├── juice/               hit flash, shake, damage numbers, hit-stop
│   └── spritesheet/         packed sheet + clip loading
├── tools/
│   └── spritegen/           offline ComfyUI drivers — never runtime
├── third_party/             GENERATED, gitignored
│   ├── ENGINE_PIN           pinned engine commit (committed)
│   ├── kaiju/               engine checkout at that pin
│   └── stock_content/       flattened engine stock content
└── games/
    └── noise-floor/         module: …/games/noisefloor
        ├── cmd/noisefloor/  main + bootstrap.GameInterface
        ├── internal/        game systems
        ├── assets/          AUTHORED assets, organised in subfolders
        ├── content/         GENERATED flat database, gitignored
        └── docs/specs/      this game's design spec
```

## Modules and the workspace

Each of `shared/` and every game is its own Go module, tied together by
`go.work`. Each `go.mod` also carries local `replace` directives mirroring the
workspace, so a game builds standalone outside the workspace too.

The engine is required as `kaijuengine.com` and replaced with the local pinned
checkout. It is never a published dependency and is never vendored into git —
`scripts/bootstrap.sh` clones it at the commit in `third_party/ENGINE_PIN`.

**The engine checkout is read-only.** Never edit files under
`third_party/kaiju/`: it is deleted and re-cloned whenever the pin changes.
Custom shaders, materials and content belong in a game's `assets/`.

## assets/ versus content/

The engine's asset database is a flat directory keyed by bare filename (see
[KAIJU-NOTES.md](KAIJU-NOTES.md)). That is hostile to humans, so:

- **`assets/`** is authored and committed, organised into `shaders/src`,
  `materials`, `textures`, `sheets`.
- **`content/`** is generated by `scripts/build-content.sh` and gitignored: the
  flattened database the engine actually loads, with GLSL compiled to SPIR-V.

`make build` regenerates `content/` first, so it can never be stale.

At runtime a game layers its own `content/` over `third_party/stock_content/`
via `kaijuboot.LayeredDatabase`, game content winning.

## Generated versus committed

Everything under `third_party/` (except `ENGINE_PIN`), every `games/*/content/`,
every `games/*/bin/`, and `scripts/env.sh` is generated. A fresh clone plus
`make bootstrap` reproduces all of it.

Sprite sheets are the deliberate exception: they are **generated offline but
committed**, so the games build with no ComfyUI and no diffusion models on
disk. No model inference ever happens at runtime.
